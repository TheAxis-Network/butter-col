Guide

Everything you need to install, run, configure and deploy butter-col.

Overview

butter-col is an interception web proxy in the same family as Ultraviolet and Scramjet. A visitor opens a site through a URL like /butter/go/https%3A%2F%2Fexample.com%2F. A service worker intercepts every request that page makes and hands it to a transport, which fetches it. The service worker then rewrites what comes back so the page keeps working from the proxy's origin.

Transports are pluggable. The built-in butter transport talks to butter-col's own OpenResty (nginx + LuaJIT) server. Others, such as @axis-network/bare-transport, talk to different backends, and visitors can switch between the ones you offer. See Transports.

Requirements

  • Node.js 20 or newer for the CLI and tooling. Development used Node 24, which the cookie-jar tests need because they load a .ts file directly.
  • OpenResty 1.21 or newer for the butter transport. The Windows build tested here is 1.27.1.2, the newest one published for Windows. On Linux and macOS, use the official packages. A serverless deployment with another transport needs no OpenResty at all.
  • A modern browser with service workers: Chrome or Edge 100+, Firefox 102+, or Safari 15.4+. Private and incognito windows sometimes disable service workers.
  • A secure context. Service workers only run on https:// or on http://localhost.

Install

In your own project

npm install @axis-network/butter-col
cp node_modules/@axis-network/butter-col/server/config.lua butter.config.lua
npx butter-col server start

That serves butter-col's frontend on http://localhost:8080/. Use --site <dir> to serve your own pages there instead; the frontend stays available at /app/. Packages → A new project walks through adding transports.

Working on butter-col itself

git clone <your fork> butter-col
cd butter-col
npm install          # links the workspaces (packages/*, examples/*)
npm run build        # builds every package
npx butter-col transport add @axis-network/bare-transport
npx butter-col transport add butter-transport-template
npm start            # this docs site on :8080, the frontend on :8080/app/

Getting OpenResty

Windows: download openresty-<version>-win64.zip from openresty.org and unzip it into .tools/, either in your project or in any parent directory. That gives you, for example, .tools/openresty-1.27.1.2-win64/nginx.exe, and the CLI finds it automatically.

Debian / Ubuntu: add the OpenResty apt repository by following the instructions on openresty.org, then sudo apt install openresty.

macOS: brew install openresty/brew/openresty.

Anywhere else, set OPENRESTY or pass --openresty /path/to/openresty.

Run the server

npx butter-col server start     # foreground; Ctrl+C stops it
npx butter-col server stop
npx butter-col server reload    # re-render config, reload without dropping connections
npx butter-col server test      # re-render and check the config (nginx -t)

In this repository, npm start, npm stop and npm run reload run those commands with --site docs --config butter.config.lua.

On every start, the CLI does three things:

  • Renders the nginx configuration from the package's templates into a runtime directory (.butter/ by default), using absolute paths to the package's Lua code and built files.
  • Copies the built-in and added transports into .butter/www/butter/transports/.
  • Downloads Mozilla's CA bundle to .butter/cacert.pem if it isn't there yet.

The server listens on port 8080 unless you pass --port. Check it's alive:

curl http://localhost:8080/butter/health
{"ok":true,"name":"butter-col","version":"0.1.0"}

Logs go to .butter/logs/error.log and .butter/logs/access.log. Proxied URLs travel in request headers rather than the request line, so the access log only shows POST /butter/fetch and not the sites people visited. The error log's startup line lists the offered transports.

First browse

  1. Open the frontend: http://localhost:8080/app/ (or / when you didn't pass --site).
  2. Type example.com (or any search) and press Go.
  3. The page opens inside the frontend's browser view. Behind the scenes, ButterController installed /butter/sw.js with scope /, read /butter/config.js (which also issues your session cookie), and encoded the URL.

If you open a /butter/go/… link before the service worker is installed, or after a hard reload (which bypasses it), the server sends a small bootstrap page. It installs the service worker and reloads.

The frontend

butter-col ships with a frontend (packages/butter-col/site/). It's served at /app/ on every server, and at / when no --site is given.

PartWhat it does
HomeA search-or-address box. Text that looks like an address opens directly; anything else is searched with your chosen engine. Underneath: the active transport, with a link to change it, and your recent sites.
Browser viewThe proxied page in a frame, below a toolbar with back, forward, reload, an address bar, home, full screen and open-in-new-tab. The address bar follows the page, including single-page apps that change their URL without reloading, and shows a warning lock for unencrypted http:// sites. The open page is kept in the frontend's URL (#<address>), so reloading the frontend reopens it.
SettingsTransport (switches for this browser), search engine (DuckDuckGo, Google, Bing, Brave Search, Startpage), theme (device, dark, light), clearing recent sites, and opening butter-col in an about:blank tab, whose address stays about:blank so the sites you browse stay out of your history.
Keyboard/ focuses the search box at home. Ctrl/⌘+L or F6 focuses the address bar. Esc in the address bar puts back the current address.

Preferences and recent sites are stored in the browser's localStorage, under the key butter-col:frontend. Nothing is sent to the server.

Your own frontend: serve any pages with --site. Import ButterController from /butter/controller.mjs to install the service worker, encode URLs (encodeUrl, resolveInput), list and switch transports, and decode the URL of a proxied page you show in an <iframe> (decodeUrl(frame.contentWindow.location.href)). site/app.js is a complete, commented example. See Packages → ButterController.

Development loop

  1. Run npm run dev -w @axis-network/butter-col in one terminal and npm start in another.
  2. Edit packages/butter-col/src/. esbuild rebuilds dist/ on every save, and the server serves dist/ directly.
  3. The service worker updates on the next navigation, because sw.js is no-cache. To force it, open DevTools → Application → Service Workers and tick Update on reload.
  4. After changing a transport, rebuild it and run butter-col transport add again, then npm run reload so the copy in .butter/ is refreshed.
  5. For Lua changes, run npm run reload. The code cache is on, so a reload is required.
  6. Run npm run check before committing.

Pure Lua modules (url, ip, cookiejar, headers, config) must stay free of ngx and of Lua 5.2+ syntax, so they run under both LuaJIT and fengari's Lua 5.3. They avoid bit operators, goto and integer division.

butter.config.lua

The server reads the file given by --config, which defaults to ./butter.config.lua and then to the package's server/config.lua. It reads it at startup and on every reload. The file returns a table that is deep-merged over the defaults in server/lua/butter/config.lua. Tables merge key by key, while lists (nameservers, transports, blocked_hosts) replace the defaults completely.

return {
  codec = "xor",
  transports = {
    { name = "butter" },
    { name = "bare", options = { server = "https://bare.example.com/" } },
  },
  default_transport = "butter",
  dns = { nameservers = { "9.9.9.9", "149.112.112.112" } },
  rate_limit = { requests = 600, window = 60 },
}

A file that fails to parse or validate stops nginx at startup with the error in .butter/logs/error.log, rather than failing later at request time.

The browser learns the public part of the configuration (prefix, codec, endpoint paths and the transport list with its options) from /butter/config.js. The server generates it from the same table, so it is the single source of truth.

nginx configuration

The CLI renders server/conf/nginx.conf.template and butter-proxy.conf.template into .butter/conf/. To manage OpenResty yourself, render them with renderServerConfig() from the Node API, or copy the rendered files. The parts worth knowing:

listen
Set with --port.
lua_shared_dict butter_dns 10m / butter_cookies 64m / butter_limit 10m
Memory shared by all workers. Cookie jars are evicted least-recently-used when butter_cookies fills up, and a warning is logged when that happens. Raise it if you have many users.
large_client_header_buffers 8 64k
Room for the X-Butter-Headers JSON on transport requests.
client_max_body_size 100m
Largest upload a proxied page can send.
location = /butter/fetch and /butter/ws
Lua prepares the request in access_by_lua. nginx's proxy_pass then streams it to the address that Lua resolved and checked. header_filter_by_lua packs the upstream status and headers into X-Butter-* headers.
butter-proxy.conf
Upstream TLS verification (proxy_ssl_verify on against the CA bundle, SNI from the original host name), timeouts, buffer sizes, and proxy_ignore_headers X-Accel-… so an upstream can never trigger an nginx internal redirect.
location ^~ /butter/transports/
Serves the transport scripts the CLI staged into the runtime directory.
location ^~ /butter/go/
Serves bootstrap.html whenever a proxied URL reaches the server, meaning the service worker didn't handle it.

Choosing a codec

Codechttps://example.com/a?b=1 becomesNotes
none/butter/go/https://example.com/a?b=1Readable, and relative URLs resolve naturally. Some intermediaries collapse // in paths.
plain/butter/go/https%3A%2F%2Fexample.com%2Fa%3Fb%3D1The default. Safe everywhere and easy to debug.
xor/butter/go/hvtrs8%2F-ezaopne%2Ccmm-a%3Db%3F1Ultraviolet's scheme. Not encryption; it only keeps the target from showing up in plain text.
base64/butter/go/aHR0cHM6Ly9leGFtcGxlLmNvbS9hP2I9MQURL-safe base64. Also not encryption.

A fragment (#section) is never encoded. It stays on the proxy URL so in-page anchors and location.hash work natively. Changing the codec breaks proxied links that people bookmarked under the old one.

HTTPS

Service workers need a secure context, so any deployment that isn't localhost must use HTTPS. The simplest setup is to terminate TLS in OpenResty itself:

server {
    listen 443 ssl;
    http2 on;
    server_name proxy.example.net;
    ssl_certificate     /etc/letsencrypt/live/proxy.example.net/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/proxy.example.net/privkey.pem;
    # ... the same root / locations as the :8080 server block ...
}

When the connection is HTTPS, the session cookie is marked Secure, and the client runtime opens WebSockets with wss://.

Behind a reverse proxy

If Caddy, Traefik, Cloudflare or another nginx sits in front:

  • Forward WebSocket upgrades for /butter/ws.
  • Keep the original Host header. The same-origin check compares Origin with Host.
  • Send X-Forwarded-Proto: https so the session cookie gets Secure.
  • Configure set_real_ip_from / real_ip_header in nginx.conf. Otherwise every visitor shares the front proxy's address and the rate limiter treats them as one client.
  • Don't let the front proxy buffer or cache /butter/fetch responses. They are per-user and are sent with Cache-Control: no-store.
  • Don't let the front proxy merge slashes or decode %2F in /butter/go/ paths.

Hardening checklist

  • Keep guard.allow_private = false. This is what stops visitors reaching 169.254.169.254, your router or localhost.
  • Run OpenResty as an unprivileged user, and firewall outbound traffic from the host if you can.
  • Use guard.allowed_hosts if the proxy is only meant for a few sites.
  • Put authentication in front (HTTP basic auth on the whole server block, or your reverse proxy's SSO). butter-col has no accounts of its own.
  • Watch .butter/logs/error.log for butter_cookies is full warnings.
  • Keep OpenResty updated. The Windows build bundles OpenSSL 1.1.1w, which is past end-of-life. Prefer a Linux deployment for anything public.
  • Read Known issues, especially the security section, before you invite anyone else.

Troubleshooting

nginx: [emerg] … cacert.pem … No such file
The CLI downloads the bundle on server start; if that failed (no internet), run npx butter-col fetch-ca later, or pass --cacert /etc/ssl/certs/ca-certificates.crt.
bind() to 0.0.0.0:8080 failed
Something else is on port 8080, possibly an earlier butter-col. Run npx butter-col server stop, or start with --port.
config.transports / config.default_transport errors at startup
The transport list is validated when the server starts. Names must be unique, lower-case and match what the script registers, and default_transport must be one of them.
module 'resty.dns.resolver' not found (Windows)
nginx.exe was started from the wrong directory. Use butter-col server start, which runs it from its own directory, or cd into the OpenResty directory and pass an absolute -p.
"Starting butter-col…" never finishes
Service workers are unavailable. Check you're on https:// or localhost, that you're not in a private window that blocks them, and that DevTools → Application doesn't show an error for /butter/sw.js.
"The service worker is installed but is not controlling this page"
Usually a hard reload (Ctrl+Shift+R), which bypasses service workers by design. Do a normal reload.
A transport shows "(failed to load)" in the launcher
The service worker couldn't importScripts() its URL. Check that /butter/transports/<name>.js returns the script (run butter-col transport add, then reload the server). Look for [butter] could not load transport in the service worker's console.
No transport named "…" is registered
The script loaded but registered a different name. The name in butter.config.lua must equal the one passed to registerTransport().
TRANSPORT_UNREACHABLE
The active transport couldn't reach its backend. For butter that's /butter/fetch on this server; for bare it's the configured Bare server. Check that the backend is up and that nothing in front of it rejects the request.
BAD_TRANSPORT_RESPONSE
The backend answered in an unexpected format. For butter this usually means a front proxy served its own error page; for bare, that the server isn't a Bare v3 server or hides the X-Bare-* headers from cross-origin readers.
BARE_… codes
Errors reported by a Bare server that butter-col has no equivalent for, such as BARE_FORBIDDEN_BARE_HEADER. See the Bare server's own logs.
DNS_FAILURE
The host doesn't resolve with the configured dns.nameservers, or they're unreachable from the server. Failures are cached for dns.negative_ttl seconds.
BLOCKED_ADDRESS
The host resolves to a private or reserved address. That's intended; see guard.allow_private.
UPSTREAM_UNREACHABLE
Connection refused or reset, or the upstream certificate failed verification. The exact reason is in .butter/logs/error.log (look for upstream SSL certificate verify error).
FORBIDDEN_ORIGIN
The transport was called from a page on a different origin. If you serve the docs from a different host than the proxy, that's the cause.
RATE_LIMITED
More than rate_limit.requests requests in one window from one address. Raise the limit, or fix the real-IP setup behind a reverse proxy.
A site loads but buttons do nothing
Open the DevTools console. Errors mentioning __butter$ point to a rewriter bug. Please report the site and the error; see Known issues for the usual suspects.

FAQ

Is this a VPN? Does it hide my IP?

Sites see the server's IP for everything that goes through the transport. But anything the runtime can't route still leaves from your browser directly; WebRTC is the main example. Treat butter-col as a convenience proxy, not as an anonymity tool.

Why OpenResty instead of Node for the server?

nginx already streams, pools connections, verifies TLS and handles WebSocket upgrades very well. The Lua code only decides whether and where to connect, and then lets nginx do the work.

Can I use Bare, Wisp or my own backend?

Yes, that's what transports are for. @axis-network/bare-transport talks to Bare v3 servers. Wisp would need a transport that wraps a client-side TLS library, such as Mercury Workshop's epoxy or libcurl.js. Anything else can be written against the transport API. butter-col's transport system plays the role that bare-mux plays for Scramjet, but it's built into butter-col rather than being a separate SharedWorker.

Can I embed the proxy in an iframe on another site?

Partly. The proxied page works, but top.location reads and frame-busting scripts touch the real cross-origin top window. The runtime can't patch that window.

Where are my cookies?

It depends on the transport. With butter, cookies are in the server's shared memory, keyed by your butter_sid session cookie; the old jar expires after cookies.session_ttl. With "client"-cookie transports such as bare, they're in the service worker's IndexedDB in your browser. Either way, clearing site data for the proxy origin starts from scratch. Switching transports also switches jars, so you may need to log in again.
