Protocol

This page specifies the wire format of the built-in butter transport, the HTTP protocol between it and butter-col's OpenResty server. One request to the transport is one upstream request, and the response streams straight back.

Other transports speak their own protocols. bare, for example, speaks Bare v3 (see Transports). The service worker messages at the end of this page are the same whichever transport is active.

All endpoints live under config.base (default /butter/). Version: 0.1.0. This is a pre-1.0 protocol, so expect changes.

/butter/fetch

Performs one HTTP request to the target. The method and body of the transport request become the method and body of the upstream request, and nginx streams both directions.

Request headers

HeaderRequiredMeaning
X-Butter-URLyesAbsolute http: or https: URL. Fragment ignored. Credentials, whitespace, control and non-ASCII characters are refused, so send URL.href.
X-Butter-HeadersnoJSON object of request headers for the upstream, e.g. {"accept":"text/html","referer":"https://example.com/"}. Non-ASCII characters must be \uXXXX-escaped.
X-Butter-Want-Cookiesno1 to receive X-Butter-Document-Cookies. Sent for documents.
Cookie: butter_sid=…noThe session; selects the cookie jar. If it's missing, a session is created and its cookie returned.

Headers from the transport request itself are dropped, except User-Agent, Accept-Language, Accept-Encoding, Content-Length and Transfer-Encoding, which are forwarded so the upstream sees the real browser. These names are refused inside X-Butter-Headers:

host connection keep-alive proxy-connection proxy-authorization te trailer
transfer-encoding upgrade content-length cookie cookie2 expect
x-forwarded-for x-forwarded-host x-forwarded-proto x-real-ip forwarded via
user-agent accept-encoding x-butter-*

The server adds Host (the original authority), Cookie (from the jar) and, if configured, User-Agent.

Successful response

The outer status is always 200, whatever the upstream returned.

HeaderMeaning
X-Butter-StatusUpstream status code, e.g. 302.
X-Butter-Status-TextStandard reason phrase for that code (nginx doesn't expose the upstream's own phrase).
X-Butter-HeadersJSON array of [name, value] pairs in upstream order. Duplicates are preserved, and Set-Cookie and hop-by-hop headers are excluded.
X-Butter-Document-CookiesIf requested: what document.cookie should read for this URL (no HttpOnly cookies).
Content-Encoding, Content-LengthCopied from upstream, so the browser decompresses the body before the service worker reads it.
Cache-Control: no-storeTransport responses are per-user and must not be cached.
Set-Cookie: butter_sid=…Only when a session was just created.

The body is the upstream body, streamed. For HEAD and for 204/304 it is empty.

Why wrap the status? If the transport answered with the upstream's 302, the browser would follow the redirect itself, and the service worker would never see the Location it needs to rewrite. A 401 with WWW-Authenticate would make the browser show an auth dialog for the proxy origin.

/butter/ws

A WebSocket tunnel. Browsers can't set headers on WebSocket handshakes, so parameters go in the query string:

GET /butter/ws?url=wss%3A%2F%2Fchat.example%2Fsocket&origin=https%3A%2F%2Fexample.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: …
Sec-WebSocket-Version: 13
Sec-WebSocket-Protocol: v1
ParameterMeaning
urlAbsolute ws: or wss: target URL (required).
originOrigin the target should see in Origin, normally the proxied page's origin. Defaults to the target's own origin.

The server applies the same rate limit, origin check, URL rules and address guard as /butter/fetch. It replaces Cookie, Origin and Referer, then passes the upgrade to the upstream. All Sec-WebSocket-* headers pass through unchanged, so the key/accept exchange, subprotocol and extension negotiation happen end to end, and nginx simply relays frames. Idle connections close after one hour without traffic. Set-Cookie on the upstream handshake response goes into the jar.

/butter/cookie

Stores a cookie written by page JavaScript (document.cookie = …).

POST /butter/cookie
Content-Type: application/json

{"url": "https://example.com/account", "cookie": "theme=dark; Max-Age=31536000; Path=/"}

The cookie string is parsed like a Set-Cookie header from url, except that it can't create an HttpOnly cookie or overwrite one. The cookie string is capped at 4 KiB and the body at 16 KiB. Responds 204 No Content.

/butter/config.js

Generated from the server's Lua configuration (butter.config.lua). Imported by the service worker and read by ButterController. It also issues the session cookie, so the session exists before the first proxied request. Static deployments get the same file from butter-col static.

self.__butter$config = {
  "version": "0.1.0",
  "prefix": "/butter/go/",
  "base": "/butter/",
  "codec": "plain",
  "transport": { "fetch": "/butter/fetch", "ws": "/butter/ws", "cookie": "/butter/cookie" },
  "client": "/butter/client.js",
  "config": "/butter/config.js",
  "transports": [
    { "name": "butter", "url": "/butter/transports/butter.js" },
    { "name": "bare", "url": "/butter/transports/bare.js", "options": { "server": "https://bare.example.com/" } }
  ],
  "defaultTransport": "butter"
};

{"ok":true,"name":"butter-col","version":"0.1.0"}

Errors

Transport errors use a real 4xx/5xx status, a JSON body {"error":{"code","message"}}, and the same object in the X-Butter-Error header. The header lets clients detect errors without reading the body.

CodeStatusWhen
RATE_LIMITED429Too many requests from this address in the current window.
FORBIDDEN_ORIGIN403Sec-Fetch-Site isn't same-origin, or Origin doesn't match Host.
INVALID_URL400Missing, malformed, wrong scheme, credentials, bad port number.
INVALID_HEADERS400X-Butter-Headers isn't an object, has a bad name or value, or has more than 100 entries.
BLOCKED_PORT403Port is on the fetch spec's bad-port list.
BLOCKED_HOST403Host is in guard.blocked_hosts or outside guard.allowed_hosts.
BLOCKED_ADDRESS403Host resolves to a private or reserved address.
DNS_FAILURE502Host didn't resolve.
UPSTREAM_UNREACHABLE502Connection refused or reset, or TLS verification failed.
UPSTREAM_TIMEOUT504Connect timeout (15 s) or read timeout (120 s for fetch).
NOT_WEBSOCKET400/butter/ws called without Upgrade: websocket.
INVALID_COOKIE400Bad /butter/cookie body.
METHOD_NOT_ALLOWED405/butter/cookie with a method other than POST.

The service worker adds its own codes when it can't get a valid answer: TRANSPORT_UNREACHABLE, BAD_TRANSPORT_RESPONSE, TRANSPORT_ERROR and INTERNAL_ERROR. They are shown on the error page and in the X-Butter-Error-Code response header.

Try it with curl

# a page through the transport (shows the wrapped status and headers)
curl -s -D - -o /dev/null http://localhost:8080/butter/fetch \
  -H 'X-Butter-URL: https://example.com/' \
  -H 'X-Butter-Headers: {"accept":"text/html"}'

# a POST with a body
curl -s http://localhost:8080/butter/fetch -X POST \
  -H 'X-Butter-URL: https://httpbin.org/post' \
  -H 'X-Butter-Headers: {"content-type":"application/json"}' \
  --data '{"hello":"butter"}'

# the guard at work
curl -s -i http://localhost:8080/butter/fetch -H 'X-Butter-URL: http://169.254.169.254/'
# HTTP/1.1 403 Forbidden
# X-Butter-Error: {"message":"169.254.169.254 points to a private or reserved address.","code":"BLOCKED_ADDRESS"}

Compared to Bare & Wisp

butter-col's transport borrows its shape from Titanium Network's Bare protocol: the target and headers travel in request headers, and the real status and headers come back in response headers. It differs in a few ways:

  • Headers: response headers are an ordered list of pairs, so duplicates survive.
  • Cookies: they live server-side, per session, rather than being forwarded by the client.
  • Encoding: compression is left to the browser.
  • Interoperability: it doesn't try to work with Bare clients.

Mercury Workshop's Wisp takes a different approach: it multiplexes raw TCP streams over a single WebSocket, so the client can do TLS itself (as in epoxy and libcurl.js) and the server never sees plaintext. The butter transport chooses the simpler, server-trusting design. The server terminates upstream TLS and therefore sees the traffic it proxies. If you need the other trade-off, it can be built as another transport rather than by changing butter-col. See Credits.

Service worker messages

ButterController and the client runtime talk to the service worker with postMessage, passing a MessagePort for the reply:

const channel = new MessageChannel();
channel.port1.onmessage = (event) => console.log(event.data); // { ok: true, result } or { ok: false, error }
registration.active.postMessage({ type: "butter:get-transport" }, [channel.port2]);
typeFieldsresult
butter:version{ version }
butter:get-transport{ active: { name, url, options }, available: [{ name, url, loaded }] }
butter:set-transportname, options?{ active }. Fails if the transport isn't configured, didn't load, or its factory throws; the choice is saved only on success.
butter:reset-transport{ active } (the configured default)
butter:socket-cookiesurl{ cookie }: the Cookie header for a WebSocket handshake. Empty for "server"-cookie transports.
butter:store-cookiesurl, setCookies{ ok: true }. Stores handshake Set-Cookie values (client jars only).

Any page on the proxy origin can send these, which includes proxied pages. Switching transports only affects that browser, but a malicious proxied page could switch it, so treat the transport choice as a preference, not a security boundary.

With a "client"-cookie transport active, the service worker also answers POST /butter/cookie itself, using the same body as the server endpoint. The request never reaches the network.
