Architecture

How a page from somewhere else ends up running on the proxy's origin, and which part is responsible for each step.

The pieces

  • The service worker (src/sw/, TypeScript) sits between proxied pages and the network.
  • A transport carries each request out. The default butter transport (src/transports/butter.ts) sends it to the server (server/, Lua on OpenResty); others, like bare, use other backends. See Transports.
  • The formatter (src/formatter/, JavaScript) is pure string-in, string-out rewriting. Both the service worker and the runtime use it.
  • The client runtime (src/client/, JavaScript) runs inside every proxied document and worker, and covers what can't be rewritten ahead of time.

Life of a request

Source paths on this page are relative to packages/butter-col/.

Here's what happens when you type example.com into the launcher, with the default butter transport:

  1. Launcher. ButterController (used by docs/launcher.js) registers /butter/sw.js with scope /. The server sends Service-Worker-Allowed: /. The launcher then fetches /butter/config.js, which also sets the butter_sid session cookie, and navigates to /butter/go/https%3A%2F%2Fexample.com%2F.
  2. Interception. The service worker's fetch handler decodes the path into the target URL https://example.com/.
  3. Headers. src/sw/request.ts copies the page's request headers. It recomputes Referer (applying the request's referrer policy as if the referrer were the target page), Origin and Sec-Fetch-Site/Mode/Dest/User.
  4. Transport. src/sw/transports.ts picks the active transport: the visitor's choice from IndexedDB, or the configured default. Its request() runs, and for butter that sends the request with the same method and body to /butter/fetch, with the target URL in X-Butter-URL and the headers in X-Butter-Headers. With a "client"-cookie transport, the service worker adds Cookie from its own jar first, and stores Set-Cookie afterwards.
  5. Access phase (Lua). The server rate-limits, checks the request came from its own origin, parses the URL strictly, validates the headers, resolves the host and rejects reserved addresses. It then replaces the request's headers, adds Cookie from the session's jar, and sets $butter_addr to the resolved IP.
  6. Proxy. nginx connects to that IP, sends SNI and Host for the original name, verifies the certificate, and streams the response back.
  7. Header filter (Lua). Set-Cookie goes into the jar. The upstream status and headers are packed into X-Butter-Status and X-Butter-Headers, and the outer response becomes a 200. Only Content-Encoding and Content-Length stay, so the browser decompresses the body itself.
  8. Rewrite. The service worker drops headers that would break the proxy (CSP, X-Frame-Options, COOP/COEP, HSTS, Clear-Site-Data, …) and rewrites Location, Refresh and Link. Then, based on the request destination, it decodes the body with the right charset and runs it through the formatter. For documents, it injects the runtime at the top of <head>.
  9. Runtime. The injected /butter/client.js runs before any of the page's own scripts and installs its hooks.

Redirects come back to the service worker as ordinary responses with a rewritten Location. The browser follows them and the new request goes through the same path. The real status is carried in a header so that the browser's network stack never acts on it: it doesn't follow redirects and doesn't show auth dialogs for 401.

Routing rules

src/sw/route.ts decides what each intercepted request is.

RequestResult
Same origin, path under /butter/go/, decodes to a URLProxy that URL. If the proxy URL has its own ?query, it replaces the target's query; this is how GET forms and ?page=2 links work.
Same origin, under /butter/go/, doesn't decode (e.g. /butter/go/img.png)A relative URL the browser resolved against the proxy URL. Resolve the tail against the requesting page's target URL.
Same origin, under /butter/butter-col's own assets: passed to the network untouched.
Same origin, anywhere else (e.g. /api/user), from a proxied pageA path-absolute URL that escaped rewriting. Resolve it against the page's target origin.
Same origin, not from a proxied pagePassthrough (the docs site).
Cross-origin, from proxied content (including about:blank frames and blob: workers)Proxy the URL as-is.
Cross-origin, from the docs sitePassthrough (Google Fonts, etc.).

The "requesting page" is found from FetchEvent.clientId. For navigations, which have no client ID, it comes from request.referrer. These fallbacks mean that a URL the rewriter missed still usually loads through the proxy instead of failing or leaking.

Lua server

The server is a thin decision layer in front of nginx's proxy module. Each request runs through these phases:

PhaseCodeWork
init_by_luabutter/init.luaLoad and validate config.lua, then preload every module.
access_by_luatransport.access_fetch / access_wsRate limit → same-origin → URL → guard (ports, hosts, DNS, reserved IPs) → headers → cookie jar → upstream variables.
contentnginx proxy_passConnect to the pinned IP with TLS verification, then stream both ways.
header_filter_by_luatransport.header_filter_*Capture cookies, pack status and headers, add the session cookie if new.
error_pagetransport.upstream_errorTurn nginx's own 502/504 into a JSON transport error.

Connecting to the address the guard checked, rather than letting nginx resolve the name again, is what defeats DNS rebinding. The name is still used for SNI, Host and certificate verification.

Shared state lives in three lua_shared_dict zones: butter_dns (resolver cache), butter_cookies (jars) and butter_limit (rate-limit counters). Nothing is written to disk.

Client runtime

The runtime (src/client/) is injected at the top of every proxied document. Its rule is that the DOM always holds proxied URLs, and the page always sees original URLs. Setters rewrite on the way in; getters un-rewrite on the way out.

Safety netA MutationObserver rewrites navigation-capable attributes (a[href], form[action], iframe[src], …) that slipped past every other hook, before anyone can click them.

Wrapped functions report their original source from Function.prototype.toString, so simple "is this native?" checks still pass. Every group of hooks is installed separately, so a missing API in one browser doesn't take down the rest.

Cookies & sessions

Where cookies live depends on the transport's cookie mode. With the default butter transport ("server" mode) they are kept on the server, not in the browser:

  • Each browser gets a random 128-bit butter_sid (HttpOnly; SameSite=Strict; Path=/, plus Secure over HTTPS).
  • Upstream Set-Cookie headers are parsed with RFC 6265 rules and stored per session in butter_cookies. The rules cover domain and path matching, Max-Age/Expires, Secure, HttpOnly, and the __Secure-/__Host- prefixes.
  • On each request the server builds the Cookie header itself. The browser never sees upstream cookies, so HttpOnly really is HTTP-only.
  • Documents are served with their document.cookie view in X-Butter-Document-Cookies. The runtime keeps a local copy, and writes are sent back to POST /butter/cookie with keepalive.

With "client"-mode transports such as bare, the service worker keeps an equivalent jar in IndexedDB. It adds Cookie to requests and stores Set-Cookie from responses. It answers POST /butter/cookie itself, and gives pages the cookies for WebSocket handshakes over a MessageChannel. HttpOnly cookies still never reach page scripts.

Storage

Every proxied site shares one real origin, the proxy's. The runtime wraps localStorage and sessionStorage in proxies that prefix keys with butter:<target origin>:, so sites can't see or clobber each other's keys. IndexedDB, the Cache API, BroadcastChannel and Web Locks are not namespaced yet; see Known issues.

WebSockets

WebSocket connections never pass through a service worker. So the runtime replaces window.WebSocket with its own class (src/client/websocket.js), which behaves like the native one: readyState, binaryType, on* handlers, ordered events, and close-code validation. It opens the socket through the active transport's connect() in the page's own realm. The headers it passes are Origin (the page's target origin), User-Agent, and the cookies from the service worker for client-jar transports.

The built-in butter transport turns new WebSocket("wss://chat.example/socket", ["v1"]) into a native socket to:

wss://proxy/butter/ws?url=wss%3A%2F%2Fchat.example%2Fsocket&origin=https%3A%2F%2Fexample.com

The server runs the same checks as for HTTP, sets Origin to the page's target origin and Cookie from the jar, and lets nginx tunnel the upgrade. The browser's Sec-WebSocket-Key, subprotocols and extensions pass straight through, so the handshake is end-to-end. Other transports tunnel it their own way; bare uses Bare v3's JSON handshake. Either way, ws.url reports the original URL.

Workers & frames

  • Dedicated and shared workers: the URL is rewritten. The service worker prepends boot data (the active transport) and importScripts() of /butter/config.js, every configured transport and /butter/client.js to classic workers. Module workers get import statements instead, with the boot data as a data: module, and are marked with ~m/ after the prefix. A "use strict" directive stays first.
  • Proxied iframes load their own runtime like any document. Every proxied document also gets a <script> for each configured transport, so transports can wrap each other in pages too.
  • about:blank / srcdoc frames: srcdoc is rewritten with the runtime injected. about:blank frames are patched by the parent the first time the page reaches into them.
  • The page's own service workers: registration is refused with a SecurityError, and controller reads as null. butter-col's own worker has to stay in control.

Security model

What the server defends (butter transport)

These protections live in the Lua server, so they apply to traffic carried by the butter transport. Other transports rely on their own backend's policy.

  • SSRF: targets must be http(s)/ws(s) on non-"bad" ports. Every resolved address is checked against loopback, RFC 1918, CGNAT, link-local (cloud metadata), multicast, documentation and other reserved IPv4/IPv6 ranges, including IPv4 embedded in IPv6. nginx then connects to the checked IP, never re-resolving.
  • Request smuggling / header injection: URLs containing whitespace, control or non-ASCII characters are refused. Header names must be RFC tokens, and values may not contain CR, LF or NUL. Hop-by-hop, Host, Cookie and forwarding headers can't be set by pages.
  • Upstream control of nginx: X-Accel-* response headers are ignored, so an upstream can't trigger internal redirects.
  • Cross-site abuse: transport endpoints refuse requests that browsers mark as cross-site, so other websites can't drive the proxy through a visitor's browser.
  • Credentials in URLs (user:pass@host) are refused.
  • Upstream TLS is verified (TLS 1.2+, SNI, Mozilla trust store).

What it does not defend

Like every same-origin interception proxy, butter-col puts every site on one origin. A malicious proxied page can, in principle, read data that other proxied sites left in shared browser storage, or script other proxied frames. The proxy also removes CSP, SRI and iframe sandbox, because they'd break rewriting. That takes away protections the sites themselves relied on. The full list is in Known issues → Security.
