Known issues

butter-col is young. Some of what follows are design limitations shared by every same-origin proxy, and some are likely bugs found while writing the code. All of it is listed here so nobody discovers it the hard way.

Testing status

What has been verified:

  • Formatter unit tests: codecs, URLs, srcset, CSS, JavaScript and HTML rewriting.
  • Cookie-jar tests, run on both the Lua jar and the service worker's TypeScript jar against the same cases.
  • Lua unit tests for URL parsing, IP ranges, header rules and configuration (including the transport list).
  • Bare transport tests against a mocked Bare v3 server.
  • TypeScript type-checking of every package.
  • End to end against OpenResty 1.27.1.2 on Windows: real HTTPS fetches with certificate verification, the private-address block, every static route, and the built butter and logged transport scripts. The transports were loaded into Node and smoke-tested over HTTP and over a WebSocket tunnel to a public echo server.

Not yet verified:

  • The full in-browser flow on real websites: service worker install, rewritten pages, the runtime hooks, the reimplemented WebSocket class, workers, forms, and cookies written by JavaScript.
  • Transport switching through ButterController.
  • The client-side cookie jar inside a real service worker.
  • The Bare transport against a real Bare server.
  • Firefox and Safari.

Expect site-specific breakage until all of this has been exercised.

Severity key

security can expose data or bypass a protection · high breaks many sites or features · medium breaks some sites · low edge case or cosmetic

Source paths on this page are relative to packages/butter-col/.

Security

securityNo CORS or SameSite emulation between proxied sites

Every request from a proxied page is sent with the session jar's cookies for the target. The service worker answers with a synthetic same-origin response, and the browser doesn't apply CORS checks to responses a service worker makes up. A malicious page opened through butter-col can therefore send authenticated requests to any other site you're logged into through the proxy, and read the responses. That includes no-cors requests, which would normally be opaque.

Where: src/sw/route.ts, src/sw/request.ts, butter/store.lua and, for client-cookie transports, src/sw/cookie-jar.ts (the same problem, with the jar in the service worker). Fix direction: send cookies only for same-site requests or when SameSite allows, and enforce CORS in the service worker using the initiator's target origin.

securityAll proxied sites share one browser origin

Proxied pages from different sites are same-origin with each other and with the docs. Any of them can script the others' frames and windows, and read IndexedDB, the Cache API and BroadcastChannel, which aren't namespaced. Only localStorage and sessionStorage are separated, and only for code that goes through the hooked getters. Every Ultraviolet-, Scramjet- and butter-col-style proxy has this property.

Mitigation: only proxy sites you trust in the same browser profile, or give each user a separate profile.

securitySite protections are removed

CSP, X-Frame-Options, COOP/COEP/CORP, HSTS, SRI (integrity) and iframe sandbox are all stripped or neutralized so rewriting can work. Sites that rely on them for XSS or clickjacking protection lose it while proxied. Plain http:// targets also appear "secure", because the proxy itself is HTTPS.

securityIt's an open proxy unless you add authentication

The same-origin check stops other websites from using visitors' browsers, but by default (allow_non_browser = true) anyone who can reach the port can drive /butter/fetch with curl. The traffic leaves from your server's IP.

Mitigation: put authentication in front, set allow_non_browser = false, restrict guard.allowed_hosts, and firewall the host.

securitypostMessage target origins are widened

postMessage(msg, "https://specific.site") is rewritten to the proxy origin, because every frame really is on the proxy origin. Any proxied frame can therefore receive messages meant for one particular site.

Where: src/client/hooks/window.js.

securityBrowser permissions, passwords and autofill are per proxy, not per site

Granting the camera, microphone, location or notifications to one proxied site grants it to every proxied site. Password managers save credentials for the proxy origin and may offer site A's password on site B.

mediumThe server sees all proxied traffic in plaintext

Upstream TLS ends at the server (unlike Wisp with client-side TLS through epoxy or libcurl.js). Whoever runs the server can read passwords and pages. That is by design, but users should know.

lowRequests with more than 200 headers aren't fully cleaned

access_fetch clears incoming headers using ngx.req.get_headers(200). Anything past the 200th header isn't cleared and is forwarded upstream. This only affects a client's own requests.

Where: butter/transport.lua → clear_request_headers. Fix: reject requests with more headers than that.

Isolation & privacy

highWebRTC, WebTransport and some beacons bypass the proxy

WebRTC isn't hooked. STUN requests leave from the browser and reveal the user's real IP, and media connects directly. WebTransport isn't proxied at all.

mediumIndexedDB, Cache API, BroadcastChannel, Web Locks and cookies on the proxy origin are shared

These aren't namespaced per target origin, so two sites that use the same database or channel names collide, and either can read the other's data.

lowBrowser history, cache and DevTools show proxy URLs

The codecs (xor, base64) only obscure the target. They aren't encryption.

Transports

securityProxied pages could switch your transport (mitigated)

The service worker answers postMessage from any page on the proxy origin, and proxied pages are on that origin. A hostile site could have sent butter:set-transport with its own options, such as a Bare server it controls, and quietly routed the visitor's later traffic through it. The service worker now accepts transport changes only from pages that are not proxied (the launcher).

A page that tricks the browser into loading a non-proxied proxy-origin page with code it controls could still get around this. No such path is known, but it hasn't been audited either.

Where: mayChangeTransport() in src/sw/index.ts. A stronger fix would be a per-entry user_options = false switch, so visitors can only pick configured options.

securityThe client cookie jar is on the shared origin (mitigated)

For "client"-cookie transports, the service worker keeps every cookie, HttpOnly included, in the IndexedDB database butter-col, on the same origin as every proxied page. The runtime now gives page code a different database when it asks for that name and hides it from indexedDB.databases().

Code that reaches an unpatched realm (see about:blank frames) could still open the real database and read the cookies.

Where: hookIndexedDB() in src/client/hooks/storage.js. Fix direction: encrypt the jar with a key that exists only in the service worker's memory, accepting that cookies are lost when it restarts, or keep cookies on a server.

securityTransport options are public; transports are trusted code

Everything in a transport's options is published in /butter/config.js, so never put tokens or passwords there. Transport scripts run inside every proxied page and in the service worker, before any site code. A malicious or compromised transport package can therefore read and change all proxied traffic. Only install transports you trust, and pin their versions.

mediumThe server's protections only cover the butter transport

The SSRF guard, DNS pinning, header sanitising, server cookie jar and rate limiting all live in the Lua server. With bare or any other transport, what the backend may reach and how it treats headers is entirely up to that backend. A Bare server on your network that has no filtering of its own can reach your internal services.

mediumSwitching transports switches cookie jars

"server" transports (the Lua jar) and "client" transports (the IndexedDB jar) don't share cookies. After switching between them, the visitor is logged out of every site, and switching back restores the old sessions. Two "client" transports do share the IndexedDB jar.

mediumEvery configured transport loads in every page

So that transports can wrap each other, each proxied document and worker loads the scripts of all configured transports, not only the active one. Each script is small (2–4 KiB) and cached, but a long list adds requests, and a transport whose script throws at load time logs errors on every page. It doesn't break the others: each script is loaded by its own <script> tag.

mediumThe Bare transport hasn't met a real Bare server yet

It follows the v3 specification and is tested against a mock. Things a real deployment might surface:

  • Servers that don't expose X-Bare-* response headers to cross-origin readers (Access-Control-Expose-Headers).
  • Servers that only implement v1 or v2.
  • Servers that send X-Bare-Headers values in an unexpected shape.

lowOpen pages keep their WebSocket transport until reloaded

HTTP switches to the new transport immediately, because it goes through the service worker. Each page's WebSocket transport was fixed when the page loaded, so it changes only on reload.

lowAxis Network transports aren't documented yet

svrls-transport, hubber-transport and feeral-transport are listed on Transports by name and purpose only, because their source wasn't available while this was written. Their specific behaviour and limitations will be added here once it is.

JavaScript rewriter

mediumRegex/division guesses can desynchronise the tokenizer

Without a parser, / after ) is treated as division and / after } as the start of a regex. Code like if (ok) /'/.test(s) breaks this guess. A misread quote then shifts what the tokenizer thinks is a string, so a location inside a real string literal could be rewritten, changing that string's contents.

Where: regexAllowed() in src/formatter/js.js. Fix direction: an AST pass (e.g. a small WASM parser), as Scramjet does with oxc.

mediumIndirect access to location isn't caught

These all reach the real Location object:

  • window["loc" + "ation"]
  • Reflect.get(window, "location")
  • Object.getOwnPropertyDescriptor(window, "location")
  • with (window) { location }
  • destructuring inside parentheses, e.g. ({ location } = window)

Reads return proxy URLs, and writes navigate away from the proxy prefix. Writes then usually land on the bootstrap page or a 404.

mediumScripts created as text at runtime are only partly covered

Covered: eval, Function, string timers, script.text/textContent/innerText and innerHTML. Not covered:

  • a text node appended to a <script>
  • blob: URL scripts and workers
  • data: modules
  • AsyncFunction / GeneratorFunction constructors
  • WebAssembly imports that touch location

lowRenaming edge cases

export const location = … renames the exported binding, so other modules' import { location } fails. export * as location has the same problem. Object.create(null) objects and Proxy set traps that write straight to the target (some reactivity libraries) can end up with a __butter$location property instead of location.

lowRewritten source is visible

Scripts that hash or inspect their own source (anti-tamper code, some captchas) see __butter$ identifiers. Column numbers in stack traces and source maps shift. "__butter$location" in {} is true.

lowimport.meta.resolve() is not rewritten

It returns a proxy URL. Usually harmless, because fetching it goes back through the proxy.

HTML & CSS rewriter

mediumDocuments, scripts and styles are buffered, not streamed

Rewritten bodies are read completely before rewriting, so a large page shows nothing until it has fully downloaded. Multi-megabyte JavaScript bundles are rewritten inside the service worker on every load, because nothing is cached.

lowThe tokenizer isn't the HTML5 algorithm

It handles common real-world markup, including raw text elements, comments, unquoted attributes and SVG. Some spec edge cases differ:

  • <noscript> content is parsed as markup.
  • Only six named entities are decoded in attribute values.
  • An unclosed quoted attribute leaves the rest of the document untouched.
  • document.write calls that split a tag across calls are rewritten piece by piece.

lowCharset handling is approximate

Charset is taken from the BOM, then Content-Type, then a regex <meta> prescan of the first 1024 bytes. XML encoding declarations and browser sniffing heuristics aren't implemented. Rewritten bodies are always re-served as UTF-8.

lowCSSOM and image-set() strings aren't rewritten

Not rewritten: insertRule, style.setProperty, CSSStyleSheet.replace, adoptedStyleSheets, and image-set("a.png" 1x) written without url(). The service worker's fallback routing usually still loads these resources through the proxy.

lowImport maps aren't rewritten

They rely on the service worker's fallback routing, which handles the usual cases.

Client runtime

mediumabout:blank frames are only patched on first access

The runtime is installed into an about:blank frame when the parent reads iframe.contentWindow or contentDocument. Code that reaches a frame through window.frames[0], window[0] or event.source gets an unpatched realm. Requests from such a realm are still caught by the service worker, but its location, cookies and storage aren't hooked.

mediumdocument.cookie is a local copy

Each document receives its cookie view when it loads. Cookies set afterwards by the server (in other tabs, frames or fetch responses) don't appear in document.cookie until the next navigation. Local writes ignore Path/Domain for the local copy, although the server applies them properly.

mediumThe page's own service workers are disabled

PWAs, offline mode and push notifications don't work. navigator.serviceWorker.ready never resolves.

lowHook coverage gaps

  • SVG href through SVGAnimatedString isn't hooked.
  • xlink:href isn't watched by the safety-net observer.
  • Attr.value and setAttributeNode aren't hooked.
  • innerHTML/outerHTML getters return proxied URLs.
  • performance entries, location.ancestorOrigins and Error stacks show proxy URLs.
  • For messages from workers and BroadcastChannel, MessageEvent.origin reports the receiving page's target origin.

lowFunction identity and hot-path cost

window.Function is a Proxy, and Function.prototype.constructor points to it. Node.prototype.textContent and Element.prototype.setAttribute are wrapped, which adds a little overhead to frameworks that call them constantly.

Service worker

highNo HTTP caching

Transport responses are no-store, and the service worker doesn't use the Cache API, so every image, script and font is fetched again on every page load. Combined with the default rate limit (1200 requests a minute), very heavy pages open in several tabs can reach RATE_LIMITED.

mediumRequest bodies are buffered

Uploads are read into memory (request.arrayBuffer()) before being sent. Large file uploads use that much memory, and streaming uploads aren't supported.

mediumHard reload and new profiles land on the bootstrap page

Ctrl+Shift+R bypasses service workers by design, so the server serves bootstrap.html, which reinstalls and reloads. If it loops, it stops after five seconds and explains why. Keepalive requests and beacons that a browser doesn't route through the service worker also reach the bootstrap page and are lost.

lowLong-lived streams depend on service worker lifetime

Server-sent events and very long downloads pass through the service worker. Browsers may end a service worker that has been busy for a long time, which cuts the stream.

lowApproximate request headers

  • Sec-Fetch-Site uses "last two labels" as the site, so a.co.uk and b.co.uk count as same-site.
  • Sec-Fetch-User is sent for every navigation.
  • Client hints (Sec-CH-UA-*) aren't forwarded unless the page itself sets them.

Cookies & sessions

securityNo public suffix list

Only single-label Domain attributes (Domain=com) are refused. A site can set a cookie for co.uk or github.io, and it will then be sent to every site under that suffix within the same session.

mediumCookies disappear on a full server restart

Jars live in lua_shared_dict memory. butter-col server reload keeps them, but server stop followed by server start logs everyone out of every site. Client jars (IndexedDB) survive restarts.

mediumSession lifetime isn't refreshed by activity

The butter_sid cookie gets Max-Age once, when it is created, and the jar's TTL only resets when a cookie changes. After cookies.session_ttl (7 days), an active user is silently given a new, empty jar.

lowRacing first requests can split a session

If the butter_sid cookie is deleted while the service worker is active, several parallel requests may each create a session before one cookie wins. Cookies set during that moment end up in the losing jars.

lowConcurrent cookie writes are best-effort

Header filters can't yield, so jar updates use a short spin lock on a shared-dict key. If two workers update the same session at the same instant and the lock is held for longer than the spin, a cookie can be lost. Under load the spin also costs a little CPU.

lowSameSite and partitioned cookies are ignored

SameSite is stored but never enforced (see the CORS issue above). Partitioned (CHIPS) isn't understood.

Server

mediumNo upstream connection pooling

proxy_pass to a variable IP doesn't use an upstream keepalive pool, so every proxied request opens a new TCP connection. TLS session reuse softens the cost, but busy servers pay a lot of handshakes. A Lua balancer with a keepalive pool would fix this.

mediumOnly the first resolved address is used

There is no failover to other A records, no Happy Eyeballs, and IPv6 is off by default. IPv6-only sites fail unless dns.ipv6 = true.

lowLost upstream details

  • Upstream reason phrases are replaced with the standard ones.
  • 1xx responses such as 103 Early Hints are dropped.
  • HTTP trailers are dropped.
  • Upstream response headers larger than 64 KiB give a 502.
  • The upstream side is always HTTP/1.1.

lowThe rate limiter is coarse

The limiter uses fixed windows, so a client can make up to twice the limit across a window boundary. Behind a reverse proxy, all users share one counter unless real_ip is configured.

lowChanging base or prefix needs matching nginx edits

The locations in nginx.conf are static. config.lua validates the values, but it can't move the nginx locations to match.

Frontend

mediumSome pages take over the whole tab

The frontend shows pages in a frame. Links with target="_top" and "frame-busting" scripts (if (top !== self) top.location = …) replace the frontend with the proxied page itself. The page still loads through the proxy, but the toolbar is gone until you go back. The runtime gives the frontend a stand-in location, so that kind of code doesn't crash.

lowToolbar state is approximate

Back and forward act on the frame's history, but the buttons are never disabled, because the frontend can't see how much history a frame has. The address bar is refreshed every half second, so a single-page app's URL can lag a moment behind. The progress bar starts when a page begins unloading and stops at load, so it doesn't reflect long-running requests.

lowPreferences are per browser

Search engine, theme and recent sites live in localStorage on the proxy origin, so they don't follow you between browsers. The transport choice is kept in the service worker's IndexedDB.

Site compatibility

highBot checks, captchas and some logins fail

Upstream connections come from nginx, whose TLS and HTTP fingerprint isn't a browser's. Cloudflare, Akamai and similar protections may show endless challenges. reCAPTCHA and hCaptcha check the embedding origin, and Google and some other sign-ins refuse what looks like an embedded or proxied browser.

mediumFrame and origin checks see the proxy

Pages that test window.top against window.self, check location.ancestorOrigins, or expect embedded players (YouTube, maps) to be cross-origin behave differently, because everything is same-origin. <a download> links to other sites now download instead of navigating.

Platform

mediumThe Windows OpenResty build is dated

The newest OpenResty published for Windows (1.27.1.2) bundles OpenSSL 1.1.1w, which is end-of-life, and the nginx project itself treats Windows as a less capable platform. It's fine for development; use Linux for anything public.

lowService workers need a secure context

Only https:// or localhost work. Some private browsing modes and enterprise policies disable service workers entirely.

Reporting a bug

Please include:

  1. The target URL, and whether it works when visited directly.
  2. Browser and version.
  3. Console errors, especially any that mention __butter$ or [butter].
  4. From the Network tab: the failing request and its X-Butter-Error or X-Butter-Error-Code header.
  5. The active transport (shown in the launcher), and the matching lines from .butter/logs/error.log when it's butter.

For rewriter bugs, the smallest snippet of HTML, CSS or JavaScript that reproduces it is gold. It can usually become a test in packages/butter-col/test/formatter.test.mjs.
