Transports

A transport is the part of butter-col that actually moves bytes between the proxy and the internet. It's pluggable: the same service worker, rewriter and runtime can run on top of butter-col's own Lua server, a Bare server, or anything else someone writes a transport for.

What a transport is

butter-col decides what to request: the URL, method, headers and body, after rewriting Referer, Origin and Sec-Fetch-*. It also decides what to do with the answer (rewrite HTML, CSS and JS, inject the runtime). The transport only decides how the request travels. Scramjet and Ultraviolet split things the same way with bare-mux: Scramjet can run over a Bare server or over Wisp (through epoxy or libcurl.js) without changing the proxy itself.

In code, a transport is an object with:

  • meta: its name, and facts butter-col needs (cookie mode, WebSocket support).
  • request(): perform one HTTP request.
  • connect(): optional; open a WebSocket.
  • init() and destroy(): optional lifecycle hooks.

It's registered under a name with registerTransport() from @axis-network/butter-transport. The full contract is on Build a transport.

Where transports run

A transport's script is a classic script. butter-col loads every configured transport into each realm that might need one, and creates an instance there on first use:

RealmLoaded byUsed for
Service workerimportScripts() at startupAll HTTP traffic of proxied pages: navigations, subresources, fetch, XHR
Proxied pages<script> tags injected at the top of <head>WebSockets (they never pass through a service worker)
Proxied workersThe prelude prepended to the worker scriptWebSockets opened by workers

Loading all of them, not only the active one, lets transports wrap or fall back to each other. The logged template wraps another transport this way.

"client"butter-col's service worker, in IndexedDB (an RFC 6265 jar that mirrors the server's).Adds Cookie to every request, stores Set-Cookie from every response, answers document.cookie writes itself, and supplies cookies for WebSocket handshakes.

butter (built in)

The original transport, now one plugin among others. It talks to butter-col's Lua server:

  • HTTP: <method> /butter/fetch, with the target in X-Butter-URL and the headers in X-Butter-Headers.
  • WebSockets: through /butter/ws.

The server pins DNS against private networks, keeps the cookie jar, and lets nginx stream the traffic. The wire format is on Protocol.

OptionDefaultMeaning
endpointconfig.transport.fetch (/butter/fetch)HTTP endpoint, relative to the proxy origin or absolute.
websocketconfig.transport.ws (/butter/ws)WebSocket endpoint.

Pointing endpoint and websocket at another butter-col server works, but its session cookie and same-origin check expect requests from its own origin. In practice, use the server that serves the pages.

bare

@axis-network/bare-transport speaks the TompHTTP Bare v3 protocol, the server type behind many Ultraviolet deployments.

  • HTTP goes to <server>v3/ with X-Bare-URL and X-Bare-Headers. Header values over 3072 bytes are split into X-Bare-Headers-N, both ways, as the spec describes.
  • WebSockets use the v3 handshake: a connect text frame, then an open message that carries the handshake's Set-Cookie values.
  • Errors are mapped onto butter-col's codes. HOST_NOT_FOUND becomes DNS_FAILURE; CONNECTION_REFUSED and CONNECTION_RESET become UPSTREAM_UNREACHABLE.
OptionRequiredMeaning
serveryesThe Bare server's root, e.g. "https://bare.example.com/" or "/bare/".
Bare servers keep no cookies, so this transport uses the service worker's client jar. A Bare server does no SSRF filtering that butter-col knows about either. Whoever runs that server decides what it may reach. If it is reachable by others, it's just as much an open proxy as butter-col's own server.

logged (template)

The template in examples/transport-template is a real, working transport. It wraps another one and logs every request and WebSocket to the console:

[logged → butter @ serviceworker] GET https://example.com/ → 200 28 ms
[logged → butter @ window] WebSocket wss://chat.example/socket []
OptionDefaultMeaning
innerThe deployment's default transport, or "butter"Transport to wrap.
innerOptionsThe inner transport's configured optionsOptions for it.

Its meta (cookie mode, WebSocket support) is copied from the transport it wraps. Copy the folder to start your own transport; see Build a transport.

Axis Network transports

Axis Network, the group behind butter-col, maintains three official transports:

TransportFocus, as described by Axis Network
svrls-transportServerless. Runs from HTML files with inline JavaScript, and can also adapt to deployers that use servers.
hubber-transportStability over speed.
feeral-transportSpeed over stability.
Their source isn't public yet. Their options, backends, cookie modes and WebSocket behaviour will be documented here once it is available. Until then this page deliberately says nothing more about them than the descriptions above. They plug in exactly like any other transport (see Installing a transport), as long as each package declares a "butter" field in its package.json.

For svrls-transport, see Without the Lua server: butter-col static produces the kind of server-free deployment a serverless transport needs.

Installing a transport

npm install @axis-network/bare-transport
npx butter-col transport add @axis-network/bare-transport
# → butter-transports/bare.js

transport add reads the package's "butter" field to find its browser script, then copies it into ./butter-transports/. It works with any transport package (or a plain .js file). butter-col server start serves everything in that folder at /butter/transports/<name>.js, alongside the built-in butter.js.

Offering transports

List the transports your deployment offers in butter.config.lua:

return {
  transports = {
    { name = "butter" },
    { name = "bare", options = { server = "https://bare.example.com/" } },
    { name = "logged", options = { inner = "bare" } },
  },
  default_transport = "butter",
}
  • name must match the name the script registers.
  • url is optional and defaults to /butter/transports/<name>.js. Set it to load a script from elsewhere.
  • options is passed to the transport's factory as JSON. It's public: visitors can read it in /butter/config.js, so never put secrets in it.
  • default_transport is used until a visitor picks another.

The server validates the list at startup: names must be unique, and the default must be one of them. Reload with npx butter-col server reload.

Switching at runtime

Visitors (or your launcher page) switch transports with ButterController, the way bare-mux's setTransport works for Scramjet:

import { ButterController } from "/butter/controller.mjs";

const butter = await new ButterController().init();
const { active, available } = await butter.getTransport();

await butter.setTransport("bare");                                   // configured options
await butter.setTransport("bare", { server: "https://other.bare/" }); // custom options
await butter.resetTransport();                                       // back to the default
  • The choice is stored in the service worker's IndexedDB, so it applies to this browser only and persists across reloads.
  • Only transports in the configuration can be selected, because only their scripts are loaded.
  • A transport that fails to start is rejected without being saved.
  • Pages that are already open keep using the old transport for WebSockets until they reload. HTTP switches immediately.

The launcher on this site's home page has a transport picker built this way.

Without the Lua server

Transports that don't need butter-col's server (such as bare) let you deploy butter-col as static files:

// butter.static.json
{
  "codec": "xor",
  "transports": [{ "name": "bare", "options": { "server": "https://bare.example.com/" } }]
}
npx butter-col static public/ --config butter.static.json

The public/ folder then holds the following, ready for any static host:

  • butter/: the service worker, the runtime, the transports and a generated config.js.
  • A launcher.
  • A 404.html that bootstraps /butter/go/… links.

Details are in Packages → Serverless deployments.
